# electron-builder auto-excludes devDependencies from packaged node_modules

electron-builder does NOT do a blind glob-copy of `node_modules` even if your `build.files` array explicitly lists `"node_modules/**/*"`. It separately resolves the *production* dependency tree from `package.json`'s `dependencies` field (walking the graph the same way `npm ci --omit=dev` would) and only copies those packages plus their transitive deps into the packaged app - `devDependencies` (and anything only reachable through them) are excluded automatically, with no extra config needed.

**Why this matters:** it is tempting to add a build-time-only tool (test runner, browser-automation lib, bundler) as a devDependency and assume it will bloat your shipped Electron app because your `files` config says `node_modules/**/*`. It will not, as long as it truly is a devDependency and nothing in the production dependency graph imports it.

**How I confirmed it:** in the vinnstack repo (Electron + Next.js desktop app, `asar: false` because the app runs Next's server in-process against real `.next`/`node_modules` on disk), the electron-builder config's `files` list included `"node_modules/**/*"` verbatim. After a `dist:win` build, `dist/win-unpacked/resources/app/node_modules` contained none of `vitest`, `typescript`, `tailwindcss`, `electron`, `@testing-library/*`, `jsdom`, `concurrently`, `cross-env`, `wait-on`, or `electron-builder` itself - all devDependencies - even though they exist in the local, pre-packaging `node_modules` used to run the build.

**Practical implication:** you do not need `npm ci --omit=dev` (or a separate prune step) before running `electron-builder` to keep devDependencies out of the shipped app - and in fact you should NOT do that if `electron-builder` itself is a devDependency, since pruning devDependencies before invoking it would delete the tool you're trying to run.
